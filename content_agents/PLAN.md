# Panghu 内容机器人计划书

## 1. 目标

在 `panghu_agent` 下建设一组独立于展示平台的内容机器人，定时收集公开信息，经过去重、事实整理、摘要生成和人工可控的审核流程后，产出可追溯的标准化内容。内容可以发布到虎博（Hublog），也可以导出到 RSS/Atom、Portal 或其他未来渠道；Hublog 只是第一批渠道适配器，不是机器人核心依赖。

第一批包含三个机器人：

| 机器人 | 目录 | 首要职责 | 建议频率 |
| --- | --- | --- | --- |
| GitHub 热门项目机器人 | `github_trending_agent` | 收集热门开源项目，生成项目变化和使用价值摘要 | 每日 1 次 |
| 国际新闻机器人 | `international_news_agent` | 汇总国际局势和重要事件，提供多来源、带时间线的简报 | 每日 1-2 次 |
| 热梗收集专家机器人 | `meme_collector_agent` | 收集公开平台上的热梗和流行表达，解释语境并附来源 | 每日 1 次 |

第一阶段的目标不是自动转载，而是生产“有来源、有时间、有边界”的摘要型内容。所有内容都应保留原始来源链接、生成身份和版本信息，并允许后续审核、重发、撤回和追溯。没有任何渠道可用时，机器人仍应能够完成采集、生成、审核和标准内容导出。

## 2. 总体架构

```text
Kubernetes CronJob / 手动运行
        |
        v
来源采集器 -> 规范化与去重 -> 证据快照 -> LLM 摘要器
                                      |
                                      v
                              规则审核 / 风险检查
                                      |
                                      v
                    标准化 ContentItem / 草稿 / 审核决策
                                      |
                                      v
                         Channel Adapters（渠道适配器）
                    ┌──────────┼──────────┬──────────┐
                    v          v          v          v
                 Hublog     RSS/Atom    Portal    其他渠道
```

每个机器人都是独立可部署单元，但共享以下基础包：

- `common/config`：环境变量、密钥引用、运行模式和时间窗口。
- `common/http`：超时、重试、限速、代理和响应大小限制。
- `common/source`：RSS、JSON API、GitHub API 等来源的统一数据结构。
- `common/dedupe`：规范化 URL、内容指纹、来源 ID 和时间窗口去重。
- `common/llm`：提示词版本、模型调用、结构化输出和 token 预算。
- `common/content_model`：平台无关的 `ContentItem`、来源、证据、标签、风险和版本模型。
- `common/review`：规则审核、人工审核状态、风险分级和发布决策。
- `common/channel`：统一渠道适配器接口、幂等键、外部 ID 映射和错误处理；Hublog 只是其中一个实现。
- `common/storage`：运行记录、原始证据、标准内容、草稿和渠道发布记录。

第一版不直接写 HBase 或 Elasticsearch。机器人核心只负责内容生产和标准化存储；每个渠道适配器负责自己的 API、权限和下游事件。Hublog 适配器通过 Hublog 业务 API 发布，由 Hublog 自己产生 Outbox 事件，避免机器人绕过业务权限。RSS/Atom 或本地 JSON 等导出渠道不需要 Hublog 即可运行。

### 2.1 平台无关的内容合同

机器人核心只输出 `ContentItem`，不保存 Hublog 专属的 `post_id`、用户关系或页面字段。建议字段包括：

- `content_id`：机器人侧生成的稳定 UUID。
- `bot_name`、`bot_version`、`prompt_version`：生成身份和版本。
- `title`、`body`、`summary`、`language`：标准正文内容。
- `source_refs`：来源名称、URL、外部 ID、发布时间和证据摘要。
- `tags`、`topics`：结构化标签和主题。
- `risk_level`、`review_status`、`review_notes`：风险与审核结果。
- `created_at`、`valid_until`、`content_hash`：时间、有效期和去重指纹。

渠道适配器根据自身能力把 `ContentItem` 映射为目标平台对象，并将结果写入 `channel_publications`。这样同一条内容可以同时导出 RSS、展示在 Portal，或发布到 Hublog，而无需重新生成。

## 3. 渠道适配层与 Hublog 首个实现

机器人核心可以在没有任何展示平台的情况下运行。接入具体渠道时，需要实现统一的 `ChannelAdapter` 接口，至少包含 `validate()`, `publish()`, `unpublish()` 和 `health_check()`。Hublog 是第一批实现，接入前需要补齐以下能力：

1. 为三个机器人建立独立的 Hublog 用户，不能共用个人账号；其他渠道不应依赖这些账号。
2. 增加服务身份认证方式：第一版使用 Kubernetes Secret 中的短期 Hublog Service Token，Hublog 侧只保存 Token 哈希和 `service:<bot-name>` 身份映射；后续可增加 Casdoor 机器客户端。不要把个人 SSO Cookie 写入机器人容器。
3. Hublog 发布接口支持 `Idempotency-Key`，格式建议为 `bot_name:source_window:content_hash`，避免重试造成重复虎博。
4. 机器人账号默认只能发布和读取必要内容，不能管理用户、删除他人内容或读取私密虎博。
5. 给标准内容保留来源元数据、机器人版本和提示词版本；适配器再按渠道能力映射到 Hublog metadata、RSS 扩展字段或 Portal 数据。
6. 为渠道发布增加可选的 `draft` 状态或审核开关：开发阶段先落草稿，生产阶段按机器人配置决定自动发布还是人工确认。
7. 记录标准内容 ID 与 Hublog 外部 ID 的映射；Hublog 不可用时，其他渠道和本地导出仍可继续工作。

## 4. 统一运行模型

### 4.1 每次运行的生命周期

1. 创建 `run_id`，记录机器人版本、配置版本、开始时间和目标时间窗口。
2. 拉取来源，保存必要的原始摘要、URL、发布时间、作者和来源标识；不默认保存受版权保护的全文或图片。
3. 规范化字段，过滤广告、重复转载、明显机器生成内容和超出时间窗口的项目。
4. 生成候选条目，计算内容指纹，检查历史发布记录。
5. 调用模型生成结构化草稿：标题、正文、标签、来源列表、置信度和风险标记。
6. 执行规则审核；高风险内容进入草稿或人工审核，低风险内容才允许发布。
7. 按配置调用一个或多个渠道适配器，记录每个渠道返回的 `external_id`、请求 ID、幂等键和状态；Hublog 适配器返回的 `post_id` 只是其中一种外部 ID。
8. 写入运行统计和失败原因，发送可观测性指标。

### 4.2 建议的共享数据表

可以使用现有 PostgreSQL 集群，但使用机器人自己的 schema 或数据库用户，避免把内容模型绑定到任何展示平台：

- `bot_runs`：每次运行的状态、时间窗口、候选数、发布数和错误信息。
- `bot_source_items`：来源 URL/外部 ID、规范化标题、内容指纹、首次发现时间和最后处理状态。
- `bot_content_items`：平台无关的标准内容、模型版本、提示词版本、审核状态和风险标记。
- `channel_publications`：`content_id`、`channel`、`external_id`、幂等键、发布时间、状态、错误信息和撤回状态。Hublog `post_id` 仅作为 Hublog 渠道的 `external_id` 保存。

原始来源只保留完成核验所需的最小字段，并设置保留期限；不把第三方全文库当作永久镜像。

## 5. GitHub 热门项目机器人

### 5.1 内容范围

每天收集过去 24 小时内有明显热度变化的公开仓库，优先考虑：

- Star、Fork、Issue、Release 或提交活跃度明显增长的项目。
- 有可读取 README、许可证和最近 Release 的项目。
- 与开发工具、AI、基础设施、数据工程和个人效率相关的项目。

### 5.2 数据来源

- GitHub REST/GraphQL API：仓库元数据、Star/Fork、Release、Issue、语言和许可证。
- GitHub Search API：按时间、主题和热度筛选候选。
- 仓库 README、Release Notes 和公开 Changelog：只摘取必要信息并链接原文。

不依赖未经授权的高频网页抓取；API 令牌放入 Vault/ExternalSecret，按 GitHub 限流规则运行。

### 5.3 发布格式

标题示例：`GitHub 今日热门：{项目名} —— {一句话价值}`

正文建议包含：

- 项目解决什么问题。
- 今天为什么值得关注：热度变化、版本更新或社区事件。
- 适合谁使用，启动成本和主要限制。
- 许可证、活跃度和安全提示。
- 原仓库、Release 和文档链接。

单个项目一条标准内容；当天项目较多时可以再生成一条“今日合集”，由渠道策略决定是否发布，避免连续刷屏。标签建议 `GitHub`、`开源`、项目领域和语言。

### 5.4 风险控制

- 不把 Star 数等同于项目质量，不使用“最强”“必装”等无证据结论。
- 检查许可证缺失、恶意安装脚本、仿冒项目和近期供应链风险。
- 对安全工具、挖矿、破解和明显违规项目默认只做风险提示或不发布。

## 6. 国际新闻机器人

### 6.1 内容范围

聚焦国际局势、外交、安全、经济、灾害和重大公共事件。第一阶段输出“事件简报”，不做未经来源支持的预测和立场裁决。

### 6.2 数据来源

优先采用有明确发布时间和公开许可/订阅规则的 RSS、官方公告和新闻机构公开页面，例如：

- 各国政府、国际组织和官方机构的公告。
- Reuters、AP、BBC、Al Jazeera 等公开 RSS 或允许访问的摘要源。
- GDELT 等新闻聚合数据，用于发现候选，不直接替代原始报道。

来源策略需要在配置文件中维护，记录来源名称、语言、可信度等级、抓取状态和许可说明。涉及冲突、伤亡、选举和金融市场时，至少要求两个相互独立的来源或一个权威一手来源。

### 6.3 发布格式

标题示例：`国际局势简报｜{日期}｜{主题}`

正文建议包含：

- 时间和地点。
- 已确认事实，区分官方说法、媒体报道和推测。
- 事件时间线。
- 各方公开立场，避免把评论写成事实。
- 可能影响和仍待确认的问题。
- 来源列表和原文链接。

标签建议 `国际新闻`、国家/地区、事件类型和日期。正文末尾固定标注“本文为公开来源摘要，不构成事实裁决或投资建议”。具体展示平台的免责声明由渠道适配器按需要追加。

### 6.4 风险控制

- 不自动发布未核实的伤亡、战争升级、政变、灾害和金融市场传闻。
- 对单一来源、翻译歧义和时间线冲突标记“待核实”，必要时转草稿。
- 对儿童、遇难者、个人隐私和现场图片不做猎奇化描述，不自动转载图片。
- 支持人工暂停某个地区或主题，避免在突发事件中连续产生错误内容。

## 7. 热梗收集专家机器人

### 7.1 内容范围

收集公开网络中正在扩散的词语、句式、挑战、梗图语境和社区表达，重点解释“它为什么突然流行”和“在什么语境下使用”。机器人不是简单搬运热搜。

### 7.2 数据来源

优先使用公开 RSS、趋势榜单、搜索趋势和允许访问的平台公开页面；平台 API、频率和版权规则通过配置管理。每个候选至少保留发现时间、来源平台、原始链接和语境样本。

不默认保存或重新发布原始梗图、视频、音乐和大段用户内容；需要视觉说明时优先使用文字描述和原链接。

### 7.3 发布格式

标题示例：`今日热梗：{梗名} —— 来源、含义与使用场景`

正文建议包含：

- 梗的名称、首次发现时间和来源平台。
- 一句话解释和典型使用场景。
- 传播路径或变体。
- 容易误用、冒犯或过时的情况。
- 原始来源链接和相关标签。

标签建议 `热梗`、平台、主题和日期。每天控制数量，宁可少生成也不要把低质量热搜全部转成平台内容。

### 7.4 风险控制

- 自动过滤仇恨、骚扰、色情、未成年人、个人隐私和明显侵权内容。
- 不发布未经核实的个人指控、电话号码、住址和聊天记录。
- 政治、灾害和公共安全相关热梗转交国际新闻机器人的审核规则，不能因为“梗”而降低核验标准。
- 保留来源和撤回机制，收到纠错后可标记标准内容并停止向相关渠道再次发布。

## 8. 调度与部署

### 8.1 Kubernetes 形态

每个机器人建议拆成两个组件：

- `CronJob`：按计划启动一次采集、生成和发布任务。
- 可选 `Deployment`：提供手动运行、草稿审核、运行状态和重试接口。

第一版可以只使用 CronJob，手动执行通过 `kubectl create job --from=cronjob/...` 完成。每个机器人使用独立 ServiceAccount、Secret、资源限制和日志标签。

### 8.2 建议时间

以下时间使用北京时间表达，真正部署时统一换算为集群时区或 UTC，并在清单中明确 `timeZone` 兼容性：

- GitHub：每天 08:00。
- 国际新闻：每天 08:30 和 20:00；突发事件不自动加频，先保留人工触发。
- 热梗：每天 18:30。

错峰运行，避免同时调用模型和同时刷屏。每个机器人设置 `concurrencyPolicy: Forbid`，单次运行超时后自动失败并告警。

### 8.3 配置和密钥

密钥统一放入现有 Vault/ExternalSecret，不进入 Git：

- GitHub API Token。
- 新闻来源需要的 API Key 或代理配置。
- 趋势来源需要的凭据。
- LLM 网关凭据。
- 各渠道凭据，例如 Hublog 机器人 Service Token；未启用的渠道不需要配置凭据。

普通配置使用 ConfigMap 或版本化 YAML，包括来源列表、发布时间窗口、模型名、审核阈值、每日最大内容数和启用的渠道列表。

## 9. 可观测性与质量指标

每次运行都要能回答：采集了多少来源、过滤了多少重复项、模型生成了什么、为什么发布或拦截，以及标准内容最终被哪些渠道接收。Hublog 渠道可进一步查询对应的 `post_id`，但它不是运行成功的必要条件。

建议指标：

- `bot_run_success_total`、`bot_run_failure_total`。
- `bot_source_items_total`、`bot_deduplicated_items_total`。
- `bot_draft_blocked_total`、`bot_channel_publication_total`。
- 发布重复率、来源缺失率、人工撤回率和用户举报率。
- 单次运行耗时、模型 token 使用量和每条标准内容成本。

日志必须包含 `bot_name`、`run_id`、`source_id`、`content_id`、`channel` 和可选的 `external_id`，但不打印 API Token、完整新闻正文或用户隐私。

## 10. 分阶段实施

### Phase 0：内容合同与渠道适配层

- 定义标准 `ContentItem`、来源证据、风险和审核状态模型。
- 定义统一 `ChannelAdapter` 接口、幂等策略和外部 ID 映射。
- 实现 Hublog Adapter 作为第一个渠道，同时实现 RSS/Atom 或本地 JSON 导出用于脱离 Hublog 验证。
- 为 Hublog 配置机器人身份、草稿开关和内容标记；这些配置只能存在于适配器层。
- 确认各渠道的撤回、审计和失败重试行为。

验收：同一 `content_id` 可以在无 Hublog 的情况下导出标准 JSON/RSS；启用 Hublog 后重复请求不会产生重复内容，且能查询外部 ID 映射。

### Phase 1：共享框架和 GitHub 机器人

- 建立共享配置、来源模型、运行记录、内容存储和渠道适配器骨架。
- 先实现 GitHub 机器人，默认草稿模式运行一周，同时验证 Hublog 和 RSS/本地 JSON 两种输出。
- 人工检查来源、摘要质量、重复率和各渠道的发布频率。

验收：连续 7 天按时运行，所有标准内容可追溯到 GitHub 来源和 `run_id`；任一渠道停用不影响采集和生成。

### Phase 2：国际新闻机器人

- 接入多语言来源、事件聚类、时间线和事实/推测分离模板。
- 默认人工审核，稳定后只对低风险主题自动发布。

验收：每条简报至少有一个权威来源，重大事件有交叉来源，无法核验的内容不会自动发布。

### Phase 3：热梗机器人

- 接入趋势发现、语境解释、敏感内容过滤和来源保留。
- 小流量运行，限制每日发布数。

验收：不转载原始受版权保护媒体，敏感内容可拦截，纠错和下架路径可用。

### Phase 4：运营和扩展

- 增加 Web 管理页：运行、草稿、审核、重试、暂停和下架。
- 在有用户反馈的渠道上，根据阅读、评论、关注和举报数据调整发布时间和内容比例；机器人核心不直接依赖这些平台指标。
- 再考虑话题流、推荐流、搜索索引和 HBase 时间线扩展。

│   └── .gitkeep
├── international_news_agent/
│   └── .gitkeep

目录只代表功能边界，不代表现在已经有可运行实现。完成计划评审后，再分别补充 `main.py`、`collector.py`、`channel adapters`、`requirements.txt`、Dockerfile、Kubernetes 清单和测试；实现顺序仍应先完成内容合同与共享框架，再实现三个机器人。
