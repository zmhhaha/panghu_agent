# 科研工作台：项目与分阶段研究流程设计

状态：设计提案，等待产品评审；2026-10-29。科研生产当前仍使用已上线的
agent-service / pi-cage 链路。本提案设计业务流程和页面，不代表新流程已经实现。

## 设计结论

把“填写主题后一次生成报告”改成围绕一个长期研究项目推进：

**研究目标 → 研究方案 → 文献与证据 → 报告初稿 → 审阅修订 → 定稿导出。**

借鉴 PPT 的项目、阶段成果、明确确认和版本修改机制。科研的两个主要决策点是：

1. **确认研究方案，开始检索**：确认要回答的问题、检索与筛选方法、来源和执行范围。
2. **确认证据与大纲，生成初稿**：看到实际找到的材料后，确定使用哪些证据、哪些问题
   仍然缺证据，以及报告各节写什么。

创建项目只需要一个问题。时间范围、资料、用途和研究深度可以逐步补充，Agent 给出
可编辑的建议。所有阶段都能保存、退出、回来继续；用户不需要记任务 ID。

首版聚焦文献研究和报告写作，可选择快速概览、主题综述或证据对比。数据分析、实验执行、
系统综述的完整方法学流程及投稿另设后续能力，不作为本次流程已经提供的功能。

## 当前问题与保留能力

当前 `app/ui/scientific_agent.py` 的 `prepare_plan` 主要重新排版表单，没有真正生成
检索方案。多个需求拼入合计最多 500 字的 topic；草稿计划存于 Gradio 会话，缺少
服务端研究项目。一次 `research.generate.v1` 同时检索、整理证据和写作，中途没有
可恢复的人工核对点。需要补文献时，固定证据章节修订无法承接，只能再建一个研究任务。

现有引用追溯、报告版本、章节索引、固定证据修订、比较与显式采用、幂等取消和成果
接收机制继续使用。PPT 值得复用的是产品机制与通用组件，而不是三套视觉方向或
PowerPoint 验收。新流程必须真实拆分执行阶段，不能仅给同一次生成加上阶段名称。

## 六个阶段

| 阶段 | 用户提供什么 | 工作台给出什么 | 主要动作 |
| --- | --- | --- | --- |
| 研究目标 | 一句话问题；可补用途、范围、已有资料 | 已保存项目、需求摘要、材料解析状态 | 生成研究方案 |
| 研究方案 | 回答必要澄清、调整建议 | 研究问题、检索词、来源、纳排标准、深度与执行范围 | **确认方案并检索** |
| 文献与证据 | 核对纳入/排除、补充资料、调整大纲 | 实际文献、访问范围、证据表、缺口、按证据组织的大纲 | **确认证据与大纲并写作** |
| 报告初稿 | 等待阶段完成或取消本次执行 | 以已确认资料为依据的可审阅草稿、来源和质量提示 | 阅读与检查 |
| 审阅修订 | 选章节并提意见；也可提出补证据要求 | 引用侧栏、修改候选、差异比较、版本历史 | 采用修改 / 补充检索 |
| 定稿导出 | 选择明确版本、处理未完成问题 | 固定的交付版本及其引用、范围、来源记录 | 确认为定稿 / 导出 |

### 研究目标：先开始，再补齐

项目首页只要求“你想研究什么”，例如“软件可重复构建有哪些实现方法和局限”。
用途、读者、时间范围、语言、必须覆盖与排除内容使用独立字段，放在可展开的补充要求中；
不再把需求压缩进一个短 topic。结构化要求可以持续编辑并有修订记录。

资料为可选项：可上传 PDF、Markdown、TXT，或登记 DOI。解析结果逐项显示；未提取
正文的文件明确显示“待处理/仅元数据”，不冒充已阅读全文。首版不承诺扫描件 OCR、
任意网页抓取或付费全文获取。上传后可以选择剔除未就绪材料再继续。

页面保存草稿不发起模型任务。用户点击“生成研究方案”后，才执行一次规划任务。

### 研究方案：给出可执行的推荐

Agent 将需求整理成一份可编辑的推荐方案：

- 主要问题与子问题、研究对象、用途和预期产物。
- 时间范围、检索来源、关键词和同义词、纳入与排除标准。
- 快速概览/主题综述/证据对比的选择、本次检索范围和停止条件。
- 当前材料覆盖、需要补充的关键问题、已知资料限制。

缺少会显著改变研究方向的信息时，先问少量关键问题；不为可默认的字段反复打断用户。
需要比较方向时可以列替代方案，默认提供一个推荐方案，不强制每次生成三套。
用户可以直接编辑字段，也可以用一句反馈重新规划。

方案明确本批检索与模型调用的上限、最长执行时间和停止条件；补充检索由用户另行发起。
界面优先展示范围与预计工作量，仅在能够可靠计费时显示费用，不让 Agent 无限扩展检索。

第一道确认绑定明确的需求、材料和方案版本。按钮“确认方案并检索”明确同时授权本次
有界检索；确认记录与执行请求在服务端持久化，不依赖网页本地状态。

### 文献与证据：写作前看见实际依据

检索完成后停在此阶段，不自动开始长篇成稿。页面分为文献表、证据摘要和可编辑大纲：

- 文献表显示题目、来源、年份、标识符、与问题的关联、建议纳入/排除及理由。
- 每份文献明确“元数据/摘要/已提供全文”，链接与核验状态各自显示。
- 证据表将子问题、可用材料、支持/反对或存在分歧的发现、尚不能回答的问题关联起来。
  自动筛选和综合属于建议；工具返回与用户选择分别记录，不把建议包装成专家结论。
- 大纲按真实证据组织：每节显示拟回答的问题、拟用材料和证据缺口，可改标题、顺序和范围。

用户可取消某篇材料、写排除理由、加入自己提供的论文，或“补充检索”。新检索形成新批次，
不改写旧观测。只保存文献选择不调用模型；点击“更新证据整理与大纲”才发起新的整理任务。

第二道确认绑定证据快照、筛选记录和大纲版本。证据不足时提供可选动作：缩小问题、补资料、
补检索，或确认以“证据有限”的范围成稿。界面不以凑够篇数作为质量目标，也不默认自动放宽
纳入标准。确认前明确展示影响正文的缺口。

### 报告初稿：按确认的大纲和证据写作

写作任务只读取第二次确认的不可变证据与大纲；不在写作过程中悄悄换资料或新增检索。
输出报告、引用、claims、证据关联和限制说明，经业务独立校验、入库读回和接收回执后
成为“待审阅草稿”。这一技术交付完成不等于用户认可结论或项目已经定稿。

进度显示“排队/整理材料/撰写/校验与保存”等可观测阶段，以及当前可执行的取消动作。
没有可靠完成比例时不显示虚构百分比、剩余时间或费用。

### 审阅修订：修改内容和增加依据有各自路径

报告中点击引用即可在右侧看到文献、证据片段及访问范围。选中章节后给出两个明确动作：

1. **用现有资料修改**：润色、调整所选章节内部的段落组织或更清晰地表达限制。固定父版本和选区，生成候选、
   比较差异，用户明确采用后才改变当前工作版本；选区外字节与固定材料保持不变。
2. **补充证据后重写**：回到文献与证据，保留已有报告，新增检索批次/材料和证据快照，
   再确认受影响的大纲与范围。用户可以限定重写章节，但跨章节引用与结论一致性仍需复核；
   不能以文字修订模式绕过新证据的确认。

批注可直接作为下一次修订反馈。新候选不会自动覆盖正在看的版本；失败也不覆盖原稿。
用户随时可以比较、放弃候选或基于指定版本继续修改。

### 定稿导出：固定交付内容

用户选择具体版本并确认定稿。定稿记录绑定报告、证据和当前未解决问题；之后继续修改
会建立新的工作草稿，旧定稿保留。这里的“定稿”是私有项目里的交付里程碑，不自动公开
分享或向外部发表。

首版沿用已经支持的 Markdown 报告与来源记录下载；草稿也可下载，但明确标注状态。
DOCX/PDF 属于后续独立导出能力，只有真实导出器和验收完成后再提供按钮。

## 页面组织

复用 PPT 的布局和交互语言，建设独立科研前端。页面以项目为中心，不以任务 ID 为中心：

- **左侧**：项目列表与阶段状态，支持搜索、最近打开、草稿/待确认/执行中/待审阅/已定稿。
- **顶部**：项目标题、自动保存状态、六步进度；始终能看见当前待办和一个主要推进按钮。
- **中央**：当前阶段的主要对象，依次为需求、方案、文献与大纲、报告、差异、交付版本。
- **右侧**：与当前选择关联的资料、引用、批注或阶段反馈。提问与调整总是附着于明确的
  方案、证据集、报告或章节，不形成另一个无法追溯的聊天会话。
- **任务抽屉**：需要时查看执行历史、失败原因和重试，普通使用不必接触 Job ID。

用户等待确认、阅读或离开页面时不占 Worker Pod。一次规划、检索、整理、写作或修订
各自是有限任务；长期保存的是项目和阶段成果。现有全局单槽队列继续使用。

## 改动后的回退与恢复

| 用户改动 | 哪些内容需要重新确认 | 哪些内容保留 |
| --- | --- | --- |
| 改项目标题、通知偏好 | 不影响研究确认 | 所有研究成果 |
| 改研究问题、来源、纳排方法或方案约定的材料范围 | 研究方案及其下游确认 | 历史批次、草稿、定稿 |
| 在方案范围内增补材料、改变文献纳入结果 | 当前证据与大纲确认 | 旧证据快照与旧报告 |
| 改大纲、用途或语言 | 受影响的写作确认；若影响问题/方法则回方案 | 旧报告和旧确认历史 |
| 选区内表达修订 | 固定本次父版本、选区与证据 | 其他正文与历史版本 |
| 修改已定稿报告 | 建立新工作草稿与新的定稿记录 | 原定稿 |

修改资料不会取消正在运行任务的已冻结输入，也不会让其结果冒充最新方案。旧运行结果
可以保留并标明来源已过期；不能自动推进当前项目的确认和定稿。

刷新/重新登录从服务器恢复项目与任务。失败停在当前阶段，已成功成果保留；先恢复已提交
任务的状态，再由用户明确发起新的失败重试，不能因前端超时重新 POST 造成双执行。

## 业务与 agent-service 的边界

科研业务拥有 Project、需求修订、Material、Plan、Confirmation、SearchBatch、EvidenceSnapshot、
Outline、ReportVersion、批注与 Finalization。业务协调器决定推进哪个阶段，并负责版本
归属、来源快照、独立校验和人机确认。Agent 服务负责中立 Job、执行和成果交接。

拟增的领域合同如下，只有完成独立验收才开放对应路由：

| 合同 | 职责 | 关键边界 |
| --- | --- | --- |
| `research.plan.v1` | 澄清问题，生成结构化方案 | 只读当前需求与资料，不执行外部检索 |
| `research.retrieve.v1` | 按已确认方案检索并记录候选文献、工具观测 | 不写最终报告，不自作纳排确认 |
| `research.outline.v1` | 对固定候选/用户选择整理证据，提出大纲 | 不添加未提供的新文献 |
| `research.draft.v1` | 按确认证据与大纲成稿 | 不自行联网扩充证据 |
| `research.revise.v1` | 复用现有固定证据章节修订机制 | 新草稿来源需通过合同兼容验收 |

新写作合同需要独立的跨阶段来源校验：受保护检索观测与 SearchBatch → 冻结的
EvidenceSnapshot → 已确认 Outline → 本次 draft。逐项核对所属项目、原始检索 attempt、
材料与观测摘要、筛选修订和确认引用；用户提供材料也保留自己的来源与解析快照。
现有 `research.generate.v1` 要求同一次 attempt 实际检索，不能直接套给只读成稿，
也不能伪造一份“本次写作已检索”的工具账本来让旧门通过。

检索后可以自动排队执行一次证据整理/大纲任务，再停在第二道人工确认；不增加无意义的
确认按钮。用户后续改动选择时按需重新整理。不能把旧 `research.generate.v1` 的一轮任务
换个名称就当作已支持“检索后停下再写作”。既有任务和报告照常恢复，新流程使用明确新合同。

业务页面不配置 Pi/Hermes、模型 URL 或供应商密钥。后台继续通过 agent-service 的已验收
绑定选引擎；技能包和引擎独立装配，业务合同不写死某一个 Agent。当前科研的文献元数据/
摘要工具和 `local-procedures-v2` 是首版能力基础；K-Dense 等能力按后续合同单独接入。

继续使用现有科研域名、SSO 身份及平台公共服务配置；本次不是重新申请 OAuth 应用、
Cloudflare 入口或给每个阶段配置供应商 Key。业务持久状态迁移需按现有数据库实际能力
设计原子提交与并发控制，不把 Gradio State 当作权威存储。

## 分阶段实施与验收

1. **项目底座与页面**：持久项目/结构化需求、资料与解析、项目列表、服务端恢复、阶段
   导航、单一主要动作；保留既有报告的真实来源，不伪造旧报告的方案确认。
2. **规划与证据链**：真实 plan/retrieve/outline 合同和工具权限，两个确认门，搜索批次、
   证据快照和引用来源；确认前不能执行相应的正式检索/写作。
3. **成稿与修订**：draft 合同、报告/证据独立校验、固定基线修订、补检索路径、批注、
   候选比较与显式采用、定稿/现有格式导出。
4. **真实项目验收与切换**：用一个实际研究主题走完整流程，验证刷新/重新登录恢复、
   幂等/取消/失败重试、改资料后的确认失效、多标签页冲突、旧任务与报告可读、全局单槽
   和等待时零任务 Worker Pod，再替换现有科研页面入口。

实施先交付最短完整主链路，再扩展参考文献导入、复杂筛选、更多技能及导出格式。用真实
任务验收，不以静态卡片、模拟进度、人工导入候选或复用旧组合通过代替新阶段验收。
