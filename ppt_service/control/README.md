# Trusted PPT control pipeline

The controller is implemented for development and deterministic integration testing. It is **disabled by default**. No model call, production deployment, invitation or PowerPoint manual acceptance is implied by these components. Formal release and invitations remain gated on the pending PowerPoint acceptance and deployment checks.

## Integration surface

`Dispatcher(sessions, config, backend, sandbox, oracle_provider=None)` uses a SQLAlchemy `sessionmaker` backed by the existing migrated PostgreSQL schema. `tick()` performs one bounded lifecycle step; `python -m ppt_service.control.dispatcher --once` executes one tick, while the same module without `--once` runs the daemon. `DATABASE_URL` and `DATA_ROOT` are required. The CLI requires PostgreSQL and does not create/migrate the schema. The default `PPT_CONTROL_STATE=disabled` never claims new work. If an existing slot is occupied, disabling admission stops and reconciles that execution before releasing it.

`RuntimeConfig` in `execution.py` exposes `disabled` and `configured` states. Real Docker admission additionally requires all of the following:

- Explicit `PPT_ALLOW_PAID_EXECUTION=true` and `PPT_NETWORK_POLICY_APPROVED=true`, set only after the parent checks the runtime template/network and the human authorizes a new real generation.
- `PPT_UPSTREAM_ENV_FILE` identifying the existing opaque proxy-only environment file. The controller checks existence and passes the path to Docker; it never reads or prints the file. The trusted proxy expects `PPT_UPSTREAM_API_KEY` there. The upstream key never enters the worker, task, database input snapshot or worker-writable mount.
- The pinned worker image `sha256:6e9bdb213f75120171d712e9bd037759cedfce6aced2caff0dae01d5fa08583a`, PPT Master commit `c350bc31e6d43b7bcf5234183d650ba8f9f4c9d7`, fixed model `gpt-6.1-sol`, fixed upstream host `custom-llm-proxy.panghuer.top` and approved IP `62.234.50.20`.
- A trusted Linux Docker host with the Docker CLI, iptables, bridge netfilter and permission to manage only this development execution environment. The public API and workers do not receive these permissions. K8s deployment/admission/SSO integration remains parent-owned.

The implementation does not flip the website's `execution_not_connected` guard or alter `control/dev_site.py`. The site must stay explicit about unavailable execution until the parent wires and verifies the configured controller.

`ExecutionBackend` defines `ready`, `create(attempt, layout)`, `reconcile(attempt)`, `observe(handle)`, `stop(handle)`, `prove_stopped(handle)` and `cleanup(handle)`. `Handle` binds the deterministic execution UID, job, attempt and fencing token; `StopProof` binds that UID and the complete observed resource set. The test `FakeBackend` exists only in `tests/control`; the production package contains no fake plans, deck generator or success fallback.

`Sandbox` defines `parse(inputs, inventory)` and `validate(private_snapshot, request)`. The concrete `DockerSandbox` runs the parser/validator in the pinned image with `network=none`, a non-root UID, a read-only root, resource limits and only the required readonly sources plus a dedicated output directory. Its own source mount is trusted installed controller code, never uploaded or generated code. Timeouts force-remove the sandbox namespace. A per-attempt UID labels sandbox containers so a replacement controller can stop them during reconciliation.

## Durable lifecycle and fencing

The existing repository provides the sole global execution slot, PostgreSQL row locks, `SKIP LOCKED`, idempotency and per-project active-job constraints. The controller does not implement a second in-memory queue or automatically retry paid work.

1. A ready controller atomically claims one queued job. It persists the deterministic execution UID and server-selected session ID before staging or starting any process.
2. Staging copies and hashes the exact immutable DB snapshot sources. Parsing runs in the separate sandbox. Before actual generation or revision admission, a trusted chart oracle must be configured and is persisted in the controller-only audit directory; a missing oracle fails before creating a worker.
3. The fixed Docker backend creates a separate worker and model proxy. Its entire resource group carries the attempt UID. The controller attaches that UID to the DB and heartbeats only the current fenced attempt.
4. A running cancellation remains `cancelling`. The controller stops every container carrying the UID, including the proxy and any sandbox/preview descendants, and verifies every observed container has `Running=false` and `Pid=0`. It does not treat Hermes completion or HTTP stop success as proof. Only then does the repository mark cancelled/release the slot, or move a completed task to validating.
5. Candidate project, home and result are copied without following links into a private readonly snapshot. Independent parsing and quality checks operate on that snapshot in the network-none sandbox. The original Actor manifest/transcript stay unchanged.
6. Publication rechecks the DB fence, cancellation/deletion and stopped state before copying immutable baselines. A plan becomes a new immutable plan revision awaiting website confirmation. A validated `prepare` checkpoint queues `generate` with the existing quota reservation and no third website gate. Generated/revised version publication is currently hard-blocked because the required independent acceptance implementation is missing; static-check success cannot create a published version.
7. An expired lease is reconciled against all old execution resources before releasing the slot. A new daemon does not resume or re-admit the old phase. Already admitted model work is never retried automatically.

The trusted in-process `progress(jid, attempt, token, stage)` helper accepts only the current phase or the real collecting/validating stage and persists an allowlisted business event. It does not accept Hermes text, tool arguments, usage claims or arbitrary owner/session/path changes. There is no public generic Hermes endpoint or arbitrary worker callback endpoint here.

## Inputs and immutable recovery

Physical paths use server-generated project, asset, job, attempt and snapshot IDs. Original asset paths must match `projects/{project_uuid}/assets/{asset_uuid}/original` exactly. Each source is rehashed and checked against the admitted DB snapshot before use. Upload names never become physical paths.

An attempt uses `projects/{project_uuid}/attempts/{job_uuid}/{attempt}-{token}/{inputs,task,home,project,result,audit,base}`. Inputs, task and base are readonly in the worker; home/project/result are writable only for this attempt. Proxy usage is written under `audit/proxy-ledger`, which is never mounted into the worker. Model proxy and worker have separate network/PID/IPC namespaces and separate mounts.

The task uses only the existing Worker allowlist: `assets` contains authorized `/work/inputs/…` paths, IDs, SHA-256, MIME and display metadata; `requirements` includes the fixed inventory/parsed-materials paths and requested revision pages. `base_version_id` is explicit. The hash remains the DB's complete snapshot hash, not the old CLI assets-only hash.

`plan_options` restores the explicit confirmed Stage1 checkpoint and full website confirmation record. `prepare` restores the explicit confirmed options checkpoint and full selected direction, page plan and production parameters. Both website confirmation contexts are retained in the immutable checkpoint for generation/revision. Revision resolves the explicitly specified version and its checkpoint, checking issuer, subject and project. No phase falls back to the project's latest runtime or latest version.

Checkpoint home bootstrap config, plugins, skills, `.env` and lazy packages are excluded from restored baselines; the worker rebuilds service policy from the fixed image. Python entrypoints start with working directory `/`, preventing a generated project module from shadowing the trusted package. Baseline files are never unpickled or executed by the controller. Independent session verification copies the stopped home into scratch, runs SQLite consistency checks and requires the selected session ID in a real sessions database before accepting a baseline.

## Parsing and validation

The source parser accepts UTF-8 Markdown, text-layer PDF, DOCX and PNG/JPEG. Limits include 25 MiB per source, ten sources, bounded total text, 150 PDF pages, image pixel/dimension limits, ZIP entry/part/total expansion/ratio limits, XML byte/node/depth limits, and rejection of entities/DTD, encrypted/active Office content, unsafe ZIP paths/links, external Office relationships and unsupported scanning/OCR cases. PDF forms and embedded files are refused. The parser does no network fetch or OCR.

The collector computes an actual complete artifact index, including unchanged files referenced by slides/quality, without rewriting the Actor record. Declared hash/size mismatches, missing declared artifacts, links, hardlinks, non-regular files and bounded size/file-count violations reject acceptance. A valid `needs_input` manifest remains `needs_input` and cannot become a plan/checkpoint/version. Its private result distinguishes `operator_permission` from `business_input`; it never disables or bypasses tool approval. The frozen public schema currently has no needs-input state/event, so that attempt is represented publicly as failed/quality-gate failure with the detailed blocked record preserved privately. A future explicit server/UI increment is needed to expose business questions safely.

The validator invokes only pinned image-owned attribution/project-validation/final-SVG scripts, on a scratch copy. It requires a real, non-empty page roster in the official final report. Generated artifacts additionally undergo bounded independent OOXML inspection, exact page count, native chart/cache/embedded-workbook checks against a trusted oracle, and PNG format/pixel checks. Worker-written reports are integrity references, never independent pass evidence. Generate must preserve the approved prepared spec/lock hashes; no spec/lock/report is fabricated.

`oracle_provider(attempt, checkpoint_manifest)` must return `{expected_charts: [...], source_sha256: [...]}` from trusted source review/configuration. Nonempty chart expectations require source hashes belonging to the admitted materials. The expected chart shape is the existing independent inspector's `{slide,categories,series:[{name,values}],type?}` contract. The oracle cannot be derived from the Actor manifest or an unreviewed self-report. The default CLI has no oracle provider, so real generate/revise admission is intentionally unavailable until parent integration supplies one.

These checks do not prove source fidelity, visual quality in PowerPoint, font reflow or editability in the target desktop application. Unknown official report shapes fail closed. The real frozen V1 fixture passed the implemented static report, session/SQLite, six-page OOXML/native-chart and existing-PNG checks, which is useful programmatic evidence but not complete publication acceptance.

## Network, usage, storage and cleanup

The Docker backend installs and checks per-attempt `DOCKER-USER` and host `INPUT` rules. Worker traffic is restricted to the fixed internal proxy IP on8080. The proxy's separate egress network permits only the approved upstream IP on443. External DNS is disabled and fixed host mappings are used; IPv6 is disabled. Traffic to host sockets/private networks has no allow rule. The default runtime cannot install/start this path without the explicit operator flags. Actual paid-path firewall/K8s isolation acceptance remains pending; parser sandbox success does not establish those boundaries.

Proxy ledger records are imported only after stop proof from the proxy-only audit mount, attributed to the DB job/attempt/phase. Failed/cancelled work remains recorded. Missing price stays null/unknown, never zero. Started requests without a completed observation are retained as interrupted/unknown. A ledger import failure preserves the ledger and a private recovery marker rather than inventing a successful reconciliation.

Retained physical source/attempt/snapshot/version/checkpoint bytes are included in controller storage checks before staging/publication. Exhaustion pauses new work; the controller does not purge projects. A filesystem/Ceph writer quota is still required for a hard per-attempt write cap; periodic scans are not that guarantee. API-wide physical-storage accounting integration remains parent-owned. Source assets, published versions and checkpoints remain until explicit project deletion; this controller does not run a retention janitor or delete a source/baseline while writers exist. Cleanup errors after a committed publication preserve its successful DB outcome and leave a private cleanup-pending marker for operator reconciliation.

Container teardown uses `docker rm --volumes` for only the backend's attempt-label-selected IDs after its existing stop proof, or the parser/validator's own freshly created nonce name (`--force`). This removes associated anonymous volumes, including the pinned worker image's implicit `/opt/data`; it does not remove named volumes or host bind data, change user-data bindings, or prune historical/orphan volumes. Backend removal errors still propagate; validation still requires successful removal and an absent container before accepting transport, otherwise retaining its existing writer quarantine. Parser teardown remains best-effort and does not certify volume removal on a failed Docker command. Focused isolated verification passed14 tests, including a never-started secure container and a network-none parser whose two captured fresh `/opt/data` volumes and container IDs were absent after the changed cleanup helpers; readonly source/published/checkpoint fixture bytes and mounted control sources stayed unchanged. Three existing real parser cases also passed. This is a source-only fix: live deployed code/images/coordinator remain unchanged and need the corrected package in a future deployment. Previously unattributable orphan volumes are untouched.

## Parse-only materials service

`python -m ppt_service.control.materials --once` claims and processes at most one queued asset or performs one recovery step. Omit `--once` for the trusted coordinator loop. Optional repeatable `--project-id UUID` limits an operator/test batch to explicit projects. This runner never claims a model Job, touches the model execution slot, starts a model proxy, reads an upstream environment file or requires `allow_paid_execution`. It can run with the complete model pipeline disabled and all paid flags false.

Apply `python -m ppt_service.server.migrate` explicitly before replacing the API image or starting this runner. Revision2 incrementally adds nullable/defaulted asset parse fields and an index; it preserves existing projects, assets, storage keys, hashes and bytes. It is transactional under the existing PostgreSQL migration advisory lock and safely handles both a fresh installation and an existing revision1 database. Startup does not silently migrate the database.

The public asset DTO adds `text_summary` (plain-text source excerpt, at most2000 characters, or an image-dimensions description) and `parse_error` (nullable fixed code). Statuses are `queued`, `parsing`, `stopping`, `ready`, `failed`; the earlier model-control parser's `succeeded` status may still be read as a completed legacy state. Safe error codes are exactly `parse_failed`, `source_unavailable`, `source_hash_mismatch`, `parse_result_mismatch`, `parse_interrupted`, `parse_aborted`. Error messages, paths, stacks, lease tokens and scope IDs are never returned to the browser. A summary is extracted material, never an AI-generated summary or claim of fact verification. Parsing does not change project revision, immutable input hash or original source bytes.

Asset leases persist `parse_attempt`, random `parse_token`, deterministic `parse_scope_uid` and `parse_lease_until`. Claims use project-then-asset `FOR UPDATE SKIP LOCKED`, skipping removed assets, deleted projects and projects with an active model job. Completion checks the same attempt/token/scope, unexpired lease, unchanged original storage key/SHA/type/size and nondeleted ownership mapping. The sandbox output must bind exactly the expected asset ID, source SHA, generated input name and inventory hash. Every scope must be proven stopped before accepting ready or failed results.

Expired/aborted work first becomes `stopping`, revoking old completion. Recovery proves all containers carrying that exact asset scope have exited before requeueing. A shared-filesystem nonblocking `flock` at `DATA_ROOT/material-locks/{assetUUID}` spans launch, parse and completion; recovery must obtain the same lock. Thus a paused old launcher cannot start a second parser after a lease replacement. If it still holds the lock, recovery waits rather than inventing stop proof. Default maximum attempts is2 (one bounded crash recovery); invalid sources become terminal failures without automatic retry. A completed asset is read normally after restart and is not parsed again. Cross-host deployment requires verified shared-filesystem flock semantics; the real integration tests cover the current single trusted Docker host.

Attempt source copies stay under `projects/{projectUUID}/material-parses/{assetUUID}/{token}/inputs`, are UUID-addressed and readonly. They are made by no-follow, ordinary-single-link reads with size/SHA verification. No uploaded or generated code is executed. Full text/Office/PDF handling remains in the existing pinned-image, network-none Docker parser; only bounded text/image metadata returns to the coordinator. Future project cleanup must first stop/reconcile outstanding asset parse scopes and acquire their locks before purging project data. Lock files themselves contain no source text. This runner does not introduce a project purge or retention janitor.

Docker sibling containers interpret bind-source paths on the **host**, not in the coordinator's mount namespace. The public API can keep `DATA_ROOT=/work/development-data`; the trusted parse coordinator must instead use the actual host-absolute data path, mounted at that same absolute path. `PPT_CONTROL_CODE_ROOT` must likewise name a trusted host-absolute control source directory mounted readonly at the same path. Do not point the coordinator at the API's container-only `/work` path.

A deployment template for the parent, using its approved image/network/opaque DB configuration, is:

```bash
docker run --rm --name ppt-materials-once \
  --user 0 --cap-drop ALL --cap-add DAC_OVERRIDE --security-opt no-new-privileges \
  --network <database-network> --env-file <database-env-file> \
  --entrypoint python \
  -e DATA_ROOT=/host/application-data \
  -e PPT_CONTROL_CODE_ROOT=/host/source/ppt_service/control \
  -e PPT_ALLOW_PAID_EXECUTION=false \
  -v /host/application-data:/host/application-data \
  -v /host/source/ppt_service/control:/host/source/ppt_service/control:ro \
  -v /usr/bin/docker:/usr/bin/docker:ro \
  -v /var/run/docker.sock:/var/run/docker.sock \
  <approved-api-image> -m ppt_service.control.materials --once
```

Only the trusted coordinator receives Docker access and DB configuration. The example's `DAC_OVERRIDE` is needed only in that trusted outer container to access the API UID10000 private data directory; dropping every outer capability made even root unable to enter the real development data path. No such capability is added to parser children. Its parser children receive neither socket nor DB/upstream environment and use `network=none`, non-root UID, readonly root, dropped capabilities, resource limits and only readonly material/control-code mounts plus a dedicated output directory. The material runner creates no Docker bridge or firewall rule. Keep website planning/generation/revision unavailable until the separately authorized model pipeline is accepted.
