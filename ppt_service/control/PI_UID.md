# Dedicated PPT Pi UID ledger

Standalone controller-only component; not wired into dispatch. `PiUIDAllocator.initialize(new_directory, UIDScope(namespace, deployment, host_pool, uid_min, uid_max))` creates an exclusive storage directory. Subsequent starts use `PiUIDAllocator(directory, same_scope)`. Call `allocate(project_id=canonical_uuid, job_id=canonical_uuid, attempt=positive_int, token=positive_int, role='pi')` before launch and bind its returned integer to the internal runtime UID. No defaults select a UID range. Attempt and token match PPT positive signed-64-bit fencing identities.

Every request requires role `pi` or `preview`, included in its canonical identity. Allocate a separate durable `preview` UID for preview processes: Pi runtime sweeps all processes with its own UID before/after execution, so a preview must never run under the Pi UID.

Every allocation, including an identical request, consumes a NEW UID. There is no binding lookup, idempotent receipt, release, reset or reuse API. Failure after commit but before receipt burns the UID. A crash before commit can roll back an unissued reservation, because nothing may launch without a successful receipt. Persist the returned binding in the future controller dispatch record before launch; failures in that integration burn the reservation. Ledger identity is canonical sorted compact JSON; namespace, deployment, host pool and configured range are pinned in the same transactionally validated database.

The storage directory itself is the exclusive initialization marker. Existing directories, missing databases, partial initialization, corruption, unknown schema/version, changed scope, and inconsistent history fail closed. Never delete the marker to recover. Reinitializing an entirely deleted directory or restoring old backups cannot be distinguished from first provisioning: **this component does not protect against operator rollback, backup restore, trusted-root tampering or lost storage**. Retire the old range and externally reserve a fresh range after such an incident. No automatic migration is supported.

SQLite >=3.37 is required for STRICT tables; otherwise only Python standard library is used. Each operation opens its own connection in `mode=rw`, uses `BEGIN IMMEDIATE`, validates exact schema and history, and returns only after commit. DELETE journaling with `synchronous=EXTRA` adds directory synchronization to FULL commit semantics. First initialization also fsyncs directories on Linux. Durable storage must honor fsync and SQLite locking; use a local reliable filesystem, not network storage. An operation scans allocation history for consistency, so this deliberately small implementation trades throughput for validation. Exhaustion is final and cannot wrap.

Production requires a Linux root controller, root-owned 0700 ledger directory, root-owned 0600 regular single-link database/sidecars, and trusted root-owned ancestors without group/other write (root-owned sticky directories are allowed). Symlinks and Windows reparse points are rejected along the ancestor chain; SQLite sidecars are inspected too. This protects against untrusted users, not concurrent malicious root filesystem mutation. Put this directory outside all worker mounts, Pi native sessions, Hermes state and artifact checkpoints. Do not share it with the scientific allocator.

The accepted range is 10001 through 2147483646 inclusive, excluding any range containing the conventional nobody UID 65534. It excludes root, system UID ranges, the existing PPT container UID 10000, and the runtime's exclusive upper bound. Operators must additionally exclude all locally assigned accounts and reserve the entire range across the declared host pool. Namespace strings are bookkeeping, **not host-global coordination**. Separate ledgers with overlapping ranges will collide. Scientific allocation currently starts at 200000 and grows without an externally bounded pool: do not assume selecting a high number avoids it. Dedicated hosts or an externally coordinated disjoint range are mandatory; scientific allocation is unchanged here.

Windows supports offline SQLite concurrency/restart tests and rejects hardlinks/reparse points. POSIX ownership, modes and directory fsync are not claimed on Windows, and the module grants no Windows production containment assurance. Run the same tests as root on Linux to verify symlink/permission checks and actual Linux filesystem behavior; Linux crash/power-loss, filesystem ownership and deployment reservation acceptance remain a deployment gate.

Run from `panghu_agent`: `python -m unittest discover -s ppt_service/tests/control -p test_pi_uid.py -v`.

Verified 2026-10-22: Windows ran 19 cases, 18 passed and one Linux ownership-policy case skipped. The parent independently ran all 19 cases on Linux as root in 6.916 seconds, with zero skips. The disposable API-image runner had network disabled, readonly root/source, no-new-privileges, only CHOWN capability, 512MiB/1CPU/pids128, and private temporary storage. It used no DB environment file, worker launch, supplier, or live service. This covers process-crash tests, concurrent processes and POSIX filesystem policy; it does not simulate power loss or reserve a production host UID range.

Tests use only temporary directories and local spawned processes, never worker startup, suppliers or live services. ## Binding verification

`PiUIDAllocator.verify(*, project_id, job_id, attempt, token, role)` returns the UID that this ledger durably allocated for exactly that binding, and never allocates. Launch code must take its UID from this method instead of trusting a caller-supplied integer or a cached copy; a number that merely looks valid is not evidence of reservation. Unknown, foreign or partially deleted bindings fail closed, and a corrupted allocation history blocks verification just as it blocks allocation. Duplicate allocations still burn fresh UIDs, but `verify` now rejects any binding with more than one allocation instead of selecting the oldest. `writers(project_id, job_id, attempt, token)` lists every committed Pi/preview UID, including duplicates, for complete stop reconciliation. The coordinator refuses a new launch when an existing attempt binding needs reconciliation; it does not silently allocate a replacement identity.

Verified 2026-10-22 on Linux as root in the disposable API-image runner (network disabled, readonly root/source, no-new-privileges, CHOWN/SETUID/SETGID/KILL only, 512MiB/1CPU/pids256, private tmpfs): `test_stop_gate` and `test_pi_uid` ran 34 cases together with zero skips, including the three new `verify` cases. On Windows the same ledger suite ran 22 cases with 21 passing and one Linux ownership-policy case skipped. This is not a production UID-pool reservation or a launch authorization.
