# 正式制作序列与修订额度账本

更新于 2026-11-16。`production_sequence_store.py` 已接入 `ProductionRunStore` 的正式成片来源登记：真实完成的 HyperFrames 整片先核验不可变模块、渲染快照与媒体字节，再建立或继承稳定制作序列。源码摘要、重新编码、复用原声或重启都不会刷新正片打磨额度。

本轮新增 `production_refinement_service.py` 和 `production_refinement_driver.py`，执行一次有界审阅、至多一次模块修订遍历和一次 HyperFrames 整片渲染。工作台通过 `film_review_client.py` 使用现有私有执行器连接；执行器用自己的已准入 v4 审阅身份执行任务，工作台不持有该通用 Agent token。HTTP／页面接线与真实业务验证需和发布记录一并核对；新增本地测试不能作为已经部署、连续播放或语音质量通过的证据。

## 身份和额度

`create(owner, project_id, source, idem)` 为首次正式制作的原始 `run_id` 建立稳定、服务端生成的 `sequence_id`。`source` 为确切的 `{run_id, version_id, sha256}`。同一 owner 的原始 run 只能对应一个序列；相同媒体或源码摘要本身不表示同一序列，也不用于生成序列身份。

之后新的制作 run 和候选版本必须使用 `bind_source(..., expected_revision=...)` 显式登记到原序列。已登记的 run 和版本不能被移到另一序列或项目，版本摘要不能悄悄变化；已登记的派生 run 不能再作为新序列的原点。此层不推断复制、另存或项目关系，后续业务入口必须携带原序列，不能为衍生候选重新调用 `create`。

当前生产请求的 `reuse_audio_from_run_id` 会保留来源 run、确切 WAV 和零 TTS 重制身份。它的 `work_budget` 是独立技术试验预算，**不是正片用户的 1+2 额度**。这类基于原视频的衍生 run 接入正式修订时，必须显式继承来源序列并通过 `bind_source` 登记确切新候选；不能因新建 run、复用原声或技术预算不同而重新建立 1+2。音频复用代码本身未在本切片修改。

每个序列总共允许：

- 一次 `automatic` 整片轮次，`round_index=0`；覆盖后续协调器的一次独立审阅、至多一次创作者修订及技术复验。
- 至多两次 `user_requested` 整片轮次，`round_index=1/2`。每次必须有明确的 `request_id`、`viewed_version_id` 和用户 `instruction`；同一用户请求不能换幂等键重复消耗两个轮次。用户追加须在首次自动轮次终结后开始。

预占即永久消耗整个轮次。失败、取消、未知提交、重启、来源版本变化均不退款，模块没有释放或重置 API。一个轮次可处理多个片段，不按镜头分配额度。实验室的委托预算和持续优化规则完全不受此模块影响。

`viewed_version_id` 绑定明确用户请求所对应的版本；账本不验证用户是否真的完整播放视频，也不伪造观看、试听、采用或审美认可。

## 后续明确需求

`reserve_requirements` 为原序列增加独立需求批次，始终绑定已经登记的确切来源版本。每项需求必须包含问题、期望及全片范围或有限时间区间。批次必须冻结正整数的 `max_agent_tasks`（最多64）和 `max_renders`（最多32），没有默认无限预算。需求可以在额度耗尽后继续提出，也可以作为更早的明确修改请求；它从不新增或重开一套 1+2。

账本负责冻结批次预算和输入身份；新增正式协调器在子任务预占时持久化消费计数，提交前检查 `max_agent_tasks` 与 `max_renders`。审阅及每个模块作者各算一次 Agent 任务，最终整片编码算一次 render；一轮内不再启动第二轮审阅或递归打磨。需求区间还必须落在真实来源整片的时长内。达到预算即停止并保留已完成工作、原有草稿和明确失败原因，不新增任务绕过预算。

## 幂等、CAS 与中断

序列单独使用一个 SQLite 文件，拒绝与含其他业务表的数据库共用路径。所有写操作使用 `BEGIN IMMEDIATE`；owner 范围的幂等键绑定 API 名、项目、完整请求及最初 CAS revision。相同原始请求重放可读取原记录的当前状态，换输入、项目、API 或最初 revision 均冲突。返回值修改不会改写已冻结记录。

序列 revision 用于来源登记和新轮次／需求批次的原子预占。具体工作另有 operation revision，用于提交与完成的 CAS。一个序列同时最多存在一个尚未终结的轮次或需求批次；不同序列互不共享额度。

生命周期：

```text
reserved ──claim_submission──> submitting ──submitted──> submitted ──finish──> completed
                                      │                           └───────> failed/cancelled
                                      └──submission_unknown──> submission_unknown
                                                                  │
                                                                  └──仅找回原执行身份
reserved ──finish──> failed/cancelled（额度仍已消耗）
```

只有成功获得 `submission_claimed=True` 的 CAS 调用者可以提交原协调器。跨过提交边界后，重启和未知响应只允许查找原 operation，不能重新提交、更换执行身份或新建同类轮次。`execution_ref` 绑定的是整个轮次／批次的协调器身份，内部审阅、创作和渲染仍需各自持久子意图；本模块不是这些子任务的提交器。

跨过提交边界的工作，终结前必须提供停止证据摘要。完成记录同时冻结结果摘要；终态不能改成另一个状态、结果或证明。账本只是保存调用方已经核验的摘要，不直接证明远端已停止、媒体有效或模型真正观察到声音和完整运动。

## 正式协调器与原制作链路

`ProductionRefinementService(path, sequences, driver)` 使用独立 SQLite 日志，先保存完整额度意图，再幂等预占既有序列。新来源必须是同一 owner／项目已经登记的 `{run_id, version_id, sha256}`，不能靠任意上传或新摘要重建轮次。未知提交只查原子任务 key，不重发；多实例通过 revision CAS 争取唯一提交权。用户请求还保留 `request_id`，页面丢失响应后可通过只读列表找回原操作。

入口为 `start(owner, project_id, source, kind=..., request_id=...)`；`user_requested` 必须传用户原指令，`requirements` 必须传带问题、预期和范围的 items 以及有限预算。自动轮次由服务端工作流触发，不由公共表单伪装。效果库完全不调用这个协调器，保持开发者持续优化规则。

预占前按真实镜头编译一次确定性的用户修改输入，连同固定说明／JSON 结构最多 12,000 字符，为作者既有 16,000 字符指令上限保留观察信息空间。单个字段合法但合计超限，也会在建立任务、占用轮次或执行审阅前拒绝，不截断用户意见。未来审阅结果本身超出剩余空间时会明确失败，不能删减用户输入或悄悄扩大作者合同。

真实 driver 沿用现有 `FilmCreationWorkflow.start_module` 和 `start_render`。修订作者获得原模块完整源码作为 `base_module`，保留原 module ID、namespace、原声、整片时钟、冻结 WikiSkill 与可用预制资源。按问题时间范围选择最早受影响场景，该场景之前的模块复用，之后的模块依次重新创作，以当前前任状态重建边界；这是保守的下游失效策略，不意味着无关片段会完全保持原视觉。用户笼统追加默认从第一场景开始，显式需求可缩小起点。

预制 Manim 等资产当前复用原资产；若问题要求修改资源本体，资源补做／依赖失效链仍需独立接通，不能声称原资源已改。协调器不重制 TTS，不会因旁白机械而误称语音改善。

审阅经过执行器的窄代理：只接受 source-bound v4 输入及对应操作的 lookup／result／cancel，不开放任意 Agent job 查询。预占额度之前先核对当前正式渲染配置、来源字节和审阅准入。代理入库与真实模型 POST 均有持久边界；恢复时保持原远端身份。

## 审阅覆盖与验收边界

当前正式审阅复用 `video.animation-review.v4`，在真实整片时长上均匀取至多 24 帧，核验模型网关确实接收这些原始帧字节。这能审阅全片时间范围内的可见布局和关系，**不等于连续看完所有帧或听完旁白**。结果明确保留 `continuous_playback_reviewed=false`、`audio_reviewed=false` 和抽帧限制，不能将零问题、渲染完成或下载当成人工审美认可。

完成操作只产生新草稿，保留原草稿及问题记录，不自动采用、试听确认或核准时序；修订后仅进行现有技术渲染校验，不再消耗第二个 Agent 审阅。实际连续运动、音画一致性、语音自然度和必要音效仍需要真实观察链路与用户验收。OpenSpec 3.5／4.x 是否可以勾选，须依相应真实证据决定。

定向测试覆盖真实序列账本的 1+2 消耗与后续明确需求、后缀修订及原模块复用、幂等、预算停止、未知提交恢复、owner／来源绑定和正式 Store 的原版本修订输入。合成 peer／媒体只验证协议与持久化，不构成动画表现力或视听验收。
