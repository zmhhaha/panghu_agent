# 正式制作序列与修订额度账本

2026-11-14。本文件说明 `production_sequence_store.py` 的独立实现边界，对应当前设计中的正式整片修订与制作序列基础。它尚未接入 `ProductionRunStore`、HTTP、工作台、Agent 或渲染器，没有部署，也不能据此勾选 OpenSpec 3.5 的完整整片审阅／修订验收。

## 身份和额度

`create(owner, project_id, source, idem)` 为首次正式制作的原始 `run_id` 建立稳定、服务端生成的 `sequence_id`。`source` 为确切的 `{run_id, version_id, sha256}`。同一 owner 的原始 run 只能对应一个序列；相同媒体或源码摘要本身不表示同一序列，也不用于生成序列身份。

之后新的制作 run 和候选版本必须使用 `bind_source(..., expected_revision=...)` 显式登记到原序列。已登记的 run 和版本不能被移到另一序列或项目，版本摘要不能悄悄变化；已登记的派生 run 不能再作为新序列的原点。此层不推断复制、另存或项目关系，后续业务入口必须携带原序列，不能为衍生候选重新调用 `create`。

当前生产请求的 `reuse_audio_from_run_id` 会保留来源 run、确切 WAV 和零 TTS 重制身份。它的 `work_budget` 是独立技术试验预算，**不是正片用户的 1+2 额度**。这类基于原视频的衍生 run 接入正式修订时，必须显式继承来源序列并通过 `bind_source` 登记确切新候选；不能因新建 run、复用原声或技术预算不同而重新建立 1+2。音频复用代码本身未在本切片修改。

每个序列总共允许：

- 一次 `automatic` 整片轮次，`round_index=0`；覆盖后续协调器的一次独立审阅、至多一次创作者修订及技术复验。
- 至多两次 `user_requested` 整片轮次，`round_index=1/2`。每次必须有明确的 `request_id`、`viewed_version_id` 和用户 `instruction`；同一用户请求不能换幂等键重复消耗两个轮次。用户追加须在首次自动轮次终结后开始。

预占即永久消耗整个轮次。失败、取消、未知提交、重启、来源版本变化均不退款，模块没有释放或重置 API。一个轮次可处理多个片段，不按镜头分配额度。实验室的委托预算和持续优化规则完全不受此模块影响。

`viewed_version_id` 绑定明确用户请求所对应的版本；账本不验证用户是否真的完整播放视频，也不伪造观看、试听、采用或审美认可。

## 后续明确需求

`reserve_requirements` 为原序列增加独立需求批次，始终绑定已经登记的确切来源版本。每项需求必须包含问题、期望及全片范围或有限时间区间。批次必须冻结正整数的 `max_agent_tasks`（最多64）和 `max_renders`（最多32），没有默认无限预算。需求可以在额度耗尽后继续提出，也可以作为更早的明确修改请求；它从不新增或重开一套 1+2。

账本当前冻结批次预算和输入身份，**尚未实现逐子任务的消费计数或执行强制**。后续协调器必须在提交实际子任务前原子记账并执行这个预算，不能把当前预算字段当成已验证的模型消费限制。时间范围的媒体时长核对也属于接线方；当前只校验合法、有限且递增的时间区间。

## 幂等、CAS 与中断

序列单独使用一个 SQLite 文件，拒绝与含其他业务表的数据库共用路径。所有写操作使用 `BEGIN IMMEDIATE`；owner 范围的幂等键绑定 API 名、项目、完整请求及最初 CAS revision。相同原始请求重放可读取原记录的当前状态，换输入、项目、API 或最初 revision 均冲突。返回值修改不会改写已冻结记录。

序列 revision 用于来源登记和新轮次／需求批次的原子预占。具体工作另有 operation revision，用于提交与完成的 CAS。一个序列同时最多存在一个尚未终结的轮次或需求批次；不同序列互不共享额度。

生命周期：

```text
reserved ──claim_submission──> submitting ──submitted──> submitted ──finish──> completed
                                      │                           └───────> failed/cancelled
                                      └──submission_unknown──> submission_unknown
                                                                  │
                                                                  └──仅找回原执行身份
reserved ──finish──> failed/cancelled（额度仍已消耗）
```

只有成功获得 `submission_claimed=True` 的 CAS 调用者可以提交原协调器。跨过提交边界后，重启和未知响应只允许查找原 operation，不能重新提交、更换执行身份或新建同类轮次。`execution_ref` 绑定的是整个轮次／批次的协调器身份，内部审阅、创作和渲染仍需各自持久子意图；本模块不是这些子任务的提交器。

跨过提交边界的工作，终结前必须提供停止证据摘要。完成记录同时冻结结果摘要；终态不能改成另一个状态、结果或证明。账本只是保存调用方已经核验的摘要，不直接证明远端已停止、媒体有效或模型真正观察到声音和完整运动。

## 后续接线顺序

1. 正式入口在首次自动审阅／修订提交前建立序列，固定原 run 和原始候选；所有后续候选保留同一序列。
2. 将原 production run 的持久 review、修订和技术复验阶段绑定一次已预占的 automatic round，保留各自原任务找回和停止核验。
3. 接入用户主动追加、明确需求、批次子任务消费及前端额度／剩余问题展示。
4. 用真实完整媒体分别验证审阅覆盖、修订结果、原声复用与边界连续性；技术通过、人工认可和正式发布继续分别记录。

当前定向测试覆盖身份与来源绑定、1+2 消耗、需求冻结、owner／项目隔离、严格幂等、CAS 并发、未知提交恢复及不可变终态，不调用模型、网络、TTS 或渲染器。
